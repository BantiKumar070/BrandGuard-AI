1. PROJECT SUMMARY
============================================================
Product: BrandGuard AI
One-line description: A brand-governance assistant that checks marketing content against a company's brand rules, flags inconsistent or risky wording, explains issues, and helps a human reviewer prepare an improved draft.

Target users: marketing teams, content writers/agencies, brand managers and review/compliance teams.

Core user journey:
1. User opens the app.
2. User selects/configures a brand profile.
3. User pastes marketing content.
4. User runs a review.
5. The system checks terminology, tone/style and potentially unsupported claims.
6. Findings show category, severity, matched snippet, explanation and suggestion.
7. User reviews suggestions and prepares a revised draft.
8. User copies/exports the draft.
9. The UI reminds the user that a human must approve content before publication.

Product principle: Help humans make better brand decisions. Do not claim legal compliance or say a flagged claim is definitely false. A claim flag means “verify against approved evidence.”

============================================================
3. RECOMMENDED STACK
============================================================
Frontend: React + Vite + JavaScript. Choose plain CSS OR Tailwind CSS; do not mix them without a reason. Lucide React is optional for icons.
Backend: Node.js + Express + JavaScript ES modules.
Review engine: deterministic rules for exact terms/patterns plus an LLM for nuanced tone/style feedback and explanations.
Data: start with a local JSON brand profile. Add MongoDB only if saving profiles/review history is necessary and time allows.
Deployment: public frontend + public backend. Configure CORS and a frontend API URL.

Never put API keys in frontend code, browser-visible Vite variables, GitHub, screenshots or public documentation. Keep secrets in backend environment variables.

============================================================
4. WHICH AI MODEL / LLM?
============================================================
Do not hard-code a model name into many files. First verify current API availability, pricing/quotas and whether the team has an API key. A ChatGPT subscription does not automatically include API usage.

Provider choices to evaluate:
- OpenAI API: a currently available small/fast model suitable for structured text review.
- Google Gemini API: a currently available Flash-class model suitable for fast text analysis.
- Anthropic API: a currently available cost-efficient Claude model if the team already has access.

Choose ONE provider for the MVP based on access, price, latency and reliable structured JSON output. Do not integrate multiple providers during Round 2 unless the first integration is already stable. Put provider logic in one small module (e.g. reviewProvider.js) so it can be swapped later.

Recommended backend function:
analyzeContent({ content, brandProfile })

Expected structured response example:
{
  "overallAssessment": "needs_review",
  "issues": [
    {
      "category": "terminology | tone | style | claim_risk",
      "severity": "low | medium | high",
      "snippet": "exact text from submitted content",
      "reason": "brief explanation based on the provided brand rules",
      "suggestion": "actionable revision"
    }
  ],
  "revisedDraft": "proposed revised content",
  "humanReviewRequired": true
}

This is a target schema, not a guarantee that the model will return valid JSON. Validate every field before rendering it. On timeout/provider failure/invalid output, show a safe message and fall back to deterministic rules when possible.

============================================================
5. SIMPLE ARCHITECTURE
============================================================
React UI -> POST /api/review -> Express API -> input validation -> deterministic rule checks -> LLM provider adapter -> validate/merge findings -> JSON response -> React results UI.

Responsibilities:
- UI: collect input and display results.
- API route: validate requests and call services.
- Rule engine: deterministic checks.
- LLM provider module: external model call only.
- Output validator: checks model response shape.
- Config: reads environment variables.

A single frontend and a single backend are enough. Avoid microservices, agents, vector databases and complex orchestration unless a real requirement demands them.

7. IMPLEMENTATION ROADMAP — FOLLOW IN ORDER
============================================================
STEP 0 — Inspect and establish a baseline
- Inspect repository, package files and existing implementation.
- If using the provided starter, install frontend/backend dependencies.
- Start frontend and backend.
- Test GET /api/health and POST /api/review.
- Confirm the review button renders results in the UI.
- Record errors before adding features. Do not replace code before understanding it.
Acceptance: app starts locally, review button works and results are visible.

STEP 1 — Stabilize the rule-based workflow
- Validate input; reject empty content and set a reasonable length limit.
- Each finding should include category, severity, snippet/match, reason and suggestion.
- Handle unexpected API responses without crashing.
- Show a disclaimer that findings are advisory and require human review.
Acceptance: test normal text, empty text, banned wording, preferred wording and API failure.

STEP 2 — Make brand guidelines configurable
- Add a simple form for brand name, voice traits, banned words, preferred terms and notes.
- Validate the profile.
- Initially keep profile state in frontend and send it with the review request; persistence can come later.
- Use a sample profile by default.
Acceptance: changing a banned word changes the next review result.

STEP 3 — Add LLM-assisted review safely
- Choose one provider based on current access, availability and budget.
- Add one backend provider adapter; send only necessary content/rules.
- Request the agreed JSON schema and validate the result server-side.
- Merge LLM findings with deterministic findings without duplicate noise.
- Claim-risk flags should ask for evidence/review, not declare claims false.
- Add timeout and safe error handling; fall back to rules if the provider fails.
- Never expose stack traces, API keys, internal prompts or raw provider errors to users.
Acceptance: valid findings render; malformed output and provider failure do not crash the app; no key is in frontend bundle or Git.

STEP 4 — Improve revised draft flow
- Show original and suggested draft separately.
- Allow copy of suggested draft.
- If time allows, allow individual suggestions to be selected before applying.
- Never silently overwrite the original.
Acceptance: user can inspect original, copy revised version and return to original.

STEP 5 — Test reliability
Test: empty input, very long input, ordinary copy, banned term, preferred term, absolute/evidence-sensitive claim, LLM timeout, invalid model JSON, backend unavailable, mobile viewport and repeated reviews. Fix blockers before adding more features.

STEP 6 — Deploy
- Deploy backend and test health endpoint.
- Configure production environment variables in hosting dashboard.
- Set frontend API URL to deployed backend.
- Deploy frontend and configure CORS.
- Test public link in private/incognito browser while signed out.
- A successful build is not proof that the deployed workflow works.

STEP 7 — Prepare Round 2 submission
- Public working project link
- Public source repository link
- Updated project PDF
- List of features that actually work
- Technology/implementation details
- Honest explanation of changes from Round 1
- Three meaningful Round 3 improvements
Never claim unimplemented features are complete.

12. API CONTRACT — KEEP BOTH SIDES IN SYNC
============================================================
Proposed endpoint: POST /api/review

Request example:
{
  "text": "Marketing copy goes here",
  "brandProfile": {
    "brandName": "Northstar",
    "voice": ["clear", "helpful"],
    "avoidWords": ["guaranteed"],
    "preferredTerms": [{"from": "cheap", "to": "affordable"}],
    "notes": "Avoid absolute promises."
  }
}

Response example:
{
  "overallAssessment": "needs_review",
  "issues": [{
    "category": "terminology",
    "severity": "high",
    "snippet": "guaranteed",
    "reason": "This phrase is on the avoid list.",
    "suggestion": "Use specific, supportable wording."
  }],
  "revisedDraft": "Suggested revised copy",
  "humanReviewRequired": true,
  "analysisMode": "rules_only"
}

This is a target contract. Update frontend and backend together if it changes. The frontend must not rely on undocumented response fields.
